There is currently no trustworthy remote safety metadata (MCP annotations like readOnlyHint are advisory and unverified for this bridge), so the stated precondition cannot be met; shipping dispatch-altering coalescing now risks changing externally visible behavior. The plan says 'defer or use warning-only if unavailable' — make deferral the committed decision for round one, with coalescing gated behind a separate future review.
B3. P4 must commit to the evidentiary standard before any fix: the mocked end-to-end fidelity tests (optional customView minLength 1, omitted field, additionalProperties false, nested, nullable union) must first demonstrate actual loss at the provider wire (e.g., SDK ToolInputSchema dropping additionalProperties, or strict:false interactions) before any schema adapter is written. The plan text allows 'fix only demonstrated loss' but needs an explicit acceptance item that no schema-mutation code lands if all fidelity tests pass green, and that the historical requiredness question is closed as 'unverifiable' in documentation rather than patched speculatively.

### Non-Blocking Suggestions
S1. Ship scope ordering: P1 (prompt/error clarity, lowest risk) and P2 (error budget, addresses the actual incident) first as independent commits; P4 fidelity tests next (tests-only unless red); P5 diagnostics after; P3 deferred. This matches the incident root cause — 32 failed list_initiatives calls — which P2 directly bounds.
S2. Missing regression cases to add: (a) interleaved failures across two distinct remote tools to ensure per-signature (not per-turn-global) budgets; (b) a failure streak broken by one genuine success then resuming, verifying reset semantics; (c) the six duplicate batches from the recovered session replayed through P3's warning-only path; (d) a polling pattern (same call, is_error=false, pending status) to confirm no false trip; (e) budget behavior when the remote returns non-typed/opaque error payloads, since deterministic classification may be unavailable.
S3. For P5, add an acceptance test that schema hashes/snapshots are stable across semantically identical but key-order-differing JSON (canonicalize before hashing), so future historical-schema comparisons are meaningful — this directly mitigates the 'no historical wire-schema capture' risk going forward.
S4. In P1, include a test asserting the unsupported-remote script error names the offending tool and suggests the direct-call path, and verify the global batch instruction prompt text no longer implies remote tools are batchable.
